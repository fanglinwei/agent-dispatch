## 2. 受众、页面与视觉方向

已确认产品服务社区活动主办者；本阶段页面只设计其对外的活动浏览和报名流程，不加入后台。实际填写者是否均为活动参与者、由主办者代填是否属于使用场景，需产品确认，不影响先编写同一报名流程的布局。

建议使用三个页面视图：活动列表 → 活动详情及同页报名表单 → 本次报名结果。具体 URL 和路由命名由前端结合现有实现确认。详情上保留“返回活动列表”；结果页提供“返回活动列表”和“查看活动详情”。没有服务器确认结果前不得进入成功视图。后退返回详情时不得触发再次提交。

视觉以信息和操作为主：白色页面、浅灰分区、深色正文、蓝色主操作；无需插图、轮播或动效。建议正文 `#172033`、次要文字 `#475569`、主按钮 `#1D4ED8` 配白字、错误文字 `#B91C1C`、分隔线 `#CBD5E1`。这些为设计值，实际样式仍须测量对比度，不能据此声称可访问性通过。状态同时使用文字和图标/结构，不依靠颜色传意。

建议正文 16px/1.5，页面标题 28px，区块标题 20px；使用系统字体，不增加外部字体依赖。桌面内容最大宽 1040px，页面边距 24px；详情正文与表单顺序单列，表单最大宽 640px，避免为短流程引入侧栏和弹窗。表单始终在文档流中，不采用悬浮按钮遮挡输入或键盘。

## 4. 完整交互状态与恢复

表中的文案均为建议稿；语义和操作关系是本岗交接要求。加载、满额、失败和结果须是互斥或可解释的明确状态，前端不得同时显示“报名成功”和“提交失败”。

| 对应需求/场景 | 展示与可用操作 | 输入、焦点与恢复 |
| --- | --- | --- |
| R1 首次加载 | 列表区域显示“正在加载活动…”，容器标记忙碌；成功后显示列表。 | 不显示空列表文案。首次载入不强制抢焦点；路由切换按第 5 节处理。 |
| R1 空列表 | “暂时没有可报名的活动”。保留标题和正常返回路径，不画假活动卡。 | 与网络失败区分；不提供指向不存在内容的详情按钮。 |
| R1/R2 读取失败 | “活动信息加载失败，请重试。”就地提供“重试”。详情首次读取失败时不展示可提交的空表单。 | 重试期间该按钮禁用并显示“重试中…”，完成后恢复；保持可用页面结构。列表重试不得跳转至报名结果。 |
| R2 详情加载成功 | 展示内容与名额状态，可报名时显示表单。 | 若是从列表进入，页面标题可编程聚焦；“填写报名信息”如需要可做页内链接，不自动聚焦第一个输入唤起手机键盘。 |
| R3 初始/输入中 | 未操作字段不预先显示错误；使用帮助文本说明已确认的格式。 | 保留原始填写值；失焦后可验证已操作字段，提交时验证全部。具体规则复用产品与 API 契约，不增加任意格式限制。 |
| R3 校验失败 | “请检查以下报名信息”，列出字段错误；没有网络提交。 | 聚焦错误摘要，提供到字段的链接；不清空任一字段。用户修改字段后清除或更新该字段错误，不提前移除表单级服务错误。 |
| R3 提交中 | 主按钮“正在提交…”，禁用再次提交；输入暂不可编辑，表单标记忙碌。 | 保留焦点与数据，不替换整张表单。必须覆盖 Enter 和连续点击；是否禁用原生字段由前端选择，但需避免禁用导致焦点丢到页面根部，并由可访问性检查确认。 |
| R4 初次就满额 | 名额区及报名区显示“名额已满，暂时无法报名”；不开放可提交表单。活动信息与返回操作可用。 | 不引入候补、订阅或预约。若可执行状态刷新沿用现有“重试/刷新信息”模式，其是否恢复开放以服务器数据为准。 |
| R4 提交后 `CAPACITY_FULL` | 表单级持久提示“名额已满，本次未完成报名。”；提交入口停止可用，仍可查看活动和返回列表。 | 立即移除提交中状态，保留原值；不将其当作普通网络错误反复发送。反馈区可编程聚焦。后续刷新名额不得清空表单；仅在重新确认可报名后允许再次提交。 |
| R5 明确成功 | 进入结果页，显示成功标题及服务器确认信息。 | 聚焦结果标题。浏览器后退不重发请求、不因旧错误恢复失败状态；如何恢复已成功视图由前端确定。 |
| R5 明确业务拒绝 | 留在表单页，展示适配层提供的用户可理解原因；可恢复时保留修改入口。 | 保留原值。权限错误或不可恢复错误不能显示成成功，不能展示原始堆栈、令牌或服务端敏感调试信息。具体错误类型由前端与测试共同确定。 |
| R6 提交网络失败 | 留在同一详情表单，显示“暂未确认报名结果，填写内容已保留。”，提供“重试”。如果适配层能证明未发送或明确失败，可使用对应更精确文案。 | 结束提交中状态，保留全部值及活动上下文；不要求重填，不自动导航，不自动连续提交。重试复用同次报名意图；安全重试与结果确认策略是前端/API 的前置契约，见第 7 节。 |
| R6 重试中/重试失败 | “正在重试…”且关闭重复操作；再次失败后保留提示和可重试状态。 | 重试仍保留值，原表单不会变为空白。恢复后字段可编辑的时机须与幂等策略一致；输入已改时是否形成新意图由前端契约决定，不能由 UI 随机生成新请求。 |

“保留输入”的本稿最低保证为同一页面/组件会话中的校验、请求失败、`CAPACITY_FULL`、重试与名额信息刷新。刷新浏览器、关闭标签页或主动跨页离开后的保存范围尚未确认，不能承诺跨会话持久保存。若产品要求离开再返回也保留，须先确认内存缓存范围与个人数据生命周期；本稿不自行加入本地持久化。

## 5. 手机、键盘、焦点与可访问性

- 窄屏以 320 CSS px 为检查起点，页面边距 16px，卡片与表单全宽单列，长标题、地点和错误文本自然折行；无水平滚动。正文缩放至 200% 时操作和错误仍可读可用；400% 缩放时按重排后的窄视口检查。
- 所有主要点击目标至少 44×44 CSS px，建议手机主按钮高 48px；相邻操作至少留 8px。只使用点击/键盘可达的操作，不以悬停、拖动或颜色作为唯一入口。
- 保持 DOM 顺序为返回导航、标题、活动信息、名额、字段、提交、反馈相关操作；Tab/Shift+Tab 可遍历所有交互元素，无正数 tabindex，不困住焦点。链接负责导航，按钮负责提交/重试；Enter 在表单内遵循提交校验和提交中防重规则。
- 键盘焦点采用清晰外框，建议 3px 主色轮廓并留 2px 间距；前端需检查实际背景下对比度和裁切。不得只靠背景色变化表示焦点，禁用态也要有可读文案和原因。
- 字段使用显式 label 与 id 关联，必填有文字/符号说明并与实际规则一致；错误用 `aria-invalid` 和 `aria-describedby` 对应。输入类型、autocomplete、inputmode 以实际字段确定；电话号码不以数值运算输入建模，不擅加固定地区规则。
- 表单校验失败聚焦带 `tabindex=-1` 的错误摘要；摘要及其相同文本不同时再次作为实时警报朗读。加载/重试进度用礼貌状态提示；未转移焦点的异步关键失败用一次警报播报，避免重复渲染反复播报。
- 路由视图切换后聚焦新页面 h1 并更新文档标题；同页提交失败只处理对应反馈焦点，不把用户送回页顶。正常输入时不因名额刷新、输入校验或 API 更新抢焦点。
- 对提交中保留在按钮上的焦点，采用原生禁用还是 `aria-disabled` 由前端结合现有组件确定；后者必须实际拦截鼠标与键盘执行，不能只改变视觉。禁用原因由邻近持久文字说明。
- 正文及关键状态文字目标对比度至少 4.5:1，大字至少 3:1；控件边界和焦点提示按相邻颜色检查至少 3:1。图标均有文字配合，纯装饰图标隐藏于辅助技术。

## 7. 输入前置、依赖顺序与待决点

1. 产品先确认 R1～R6 完整流程、活动可见内容、报名字段/规则、容量满后允许的下一步，以及“保留输入”的离开页面范围。本稿提供已确认目标下的状态布局，不修改需求优先级。
2. 前端核对实际活动字段、名额数值语义及 REST 响应，定义加载、业务错误、`CAPACITY_FULL`、成功与网络结果未知的展示契约；确定安全重试、重复请求、成功后返回的处理。没有幂等性或查询结果能力时，提交超时后的无重复报名重试仍是阻塞实现的契约缺口，不能由一个“重试”按钮补足。
3. UI 按确认后的字段和错误契约校正文案与交互，交付前端和测试；主代理处理跨岗矛盾。颜色或排版的局部适配可在保持本文状态、可访问性与层级的前提下建议调整，不能自行改变流程。
4. 前端完成实施后，先交本阶段构建身份及实际页面；测试执行所需用例。UI 再做设计符合性复核，缺陷交主代理分配；本次仅供稿，无页面、代码和行为检查。
