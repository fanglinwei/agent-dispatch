## 2. 范围、受众与完成边界

**已确认范围：**交付社区活动报名工具的可交付第一版。项目服务社区活动主办者；在“不含活动后台”的本阶段，建议把前台主流程定义为参与者查看活动并提交报名，主办者通过现有来源提供活动。实际活动维护方式不在本次新增范围内。此参与者视角是产品建议，待整合版确认。

**产品建议的最小完成边界：**用户能够在手机或键盘环境中，从活动列表进入同一活动详情、填写有效表单、提交一次报名并理解实际结果；遇到名额满或网络失败时，当前状态和下一步明确，失败后保留本次输入，不以清空重填作为恢复手段。

- 六项需求共同组成第一版出口，不能把只有列表和详情的页面标成报名流程已完成。
- 排除支付、登录和活动后台；建议同时不增加搜索筛选、候补队列、多人代报名、取消报名、通知订阅、离线提交及跨设备草稿。这些不是六项流程的必要条件。
- R6 的最小保留范围建议为：当前页面本次表单在网络失败与手动重试之间不丢失。刷新、关闭页面、离开后返回的持久化草稿尚未获确认，不默认引入浏览器存储。
- 容量是否有余量由最新服务端报名结果裁决。已有模型可供页面预提示，不能保证用户点击提交时仍有名额。
- 页面显示成功必须有本次提交的有效成功响应。超时、断网或响应无法确认时显示“结果未确认”，不能显示成功，也不能断言服务端一定未受理。

## 3. 端到端流程与恢复分支（产品建议）

下表定义玩家可见的产品状态和动作；具体 Vue 状态枚举、接口字段、组件布局和焦点实现分别由前端、UI 唯一定义，避免复制成第二套技术契约。

| 环节与入口 | 用户应看到与可以执行的动作 | 分支与恢复 | 离开本环节的条件 |
| --- | --- | --- | --- |
| 活动列表：首次进入或返回列表 | 加载期间有明确状态；加载成功后可识别活动并进入其详情。列表项的最小身份、标题及可展示信息由现有数据核实后确定，不编造时间、地点或图片。 | 空列表呈现“当前暂无活动”和可用返回路径；加载失败提供说明和手动重试，重试恢复列表而不误入其他活动。加载、空、失败不可混成同一空白页面。 | 选中活动时，详情与所选活动身份一致；或用户留在明确的空/失败状态。 |
| 活动详情：来自列表或现有可用详情入口 | 显示同一活动内容及报名入口；可返回列表。页面中应能理解报名的对象，容量状态与操作是否可用一致。 | 活动不存在、已不可访问或详情加载失败时不展示可提交的空壳表单；给出返回列表或重试动作。具体错误文案由 UI 设计，错误分类由前端核实接口。 | 取得可用活动详情后进入报名；若容量满则进入满额提示分支。 |
| 报名表单：详情可报名 | 展示已确认字段、必填和格式说明；键盘可顺序填写和提交，触控目标由 UI 规格定义。用户能辨认当前活动。 | 校验不通过时，错误关联到相应字段，保留全部已输入内容，并使首个错误可被定位；修正后可再次提交。不能通过静默禁用让用户猜测原因。 | 客户端校验通过、当前没有同一表单的进行中请求，才发送报名请求。 |
| 提交进行中：校验通过 | 明确显示提交进行中；同一表单不能因重复点击或回车产生并发重复请求。 | 不以客户端停用按钮代替服务端去重。按钮、回车、重试统一受同一提交状态约束；请求未结束前不可新起一次同表单提交。超时的认定由前端契约定义。 | 获得明确响应，或进入网络/结果未确认状态。 |
| 名额满：详情已满或服务端返回 `CAPACITY_FULL` | 明确提示该活动目前已满，停止提供继续提交同一报名的路径；保留已输入信息供用户理解发生了什么，并提供返回列表动作。 | 列表或详情显示有余量、提交时服务端判满是正常竞争分支，必须转入同一满额提示。不能当普通网络失败反复重试，也不增加未经确认的候补功能。若允许刷新容量后重开表单，需由接口和 UI 明确条件。 | 用户返回列表；或在有明确新容量证据且产品确认该行为后重新开放报名。 |
| 报名成功：服务端明确确认 | 明确显示成功并关联当前活动；若接口确实返回报名凭证，可展示该凭证，不能生成虚构编号。提供返回列表动作。 | 成功展示态中不能保留可立即再次提交同一报名的主按钮；页面刷新后的结果恢复策略待核实，不假定已有查询接口。 | 用户读懂成功结果并可返回列表；该次表单提交闭环结束。 |
| 明确业务拒绝：服务端可识别的字段、权限或其他业务错误 | 说明当前未完成的原因和可执行下一步；可修正的字段错误回到原表单，保留输入。无需登录的范围不得因未知错误自行增加登录页。 | `CAPACITY_FULL` 使用专门满额分支；权限拒绝及重复报名按已核实服务端语义说明，不将所有错误归为网络失败。未知错误保留输入并给出适当恢复路径，不显示成功。 | 修正可修复问题后再次提交，或用户返回列表；不可修复原因需说明。 |
| 网络失败或结果未确认：断网、超时、响应中断 | 告知本次结果暂时未确认，当前输入保留，提供显式“重试”动作和返回路径；不在后台无限自动重试。 | 用户重试时继续使用当前活动及保留的输入；若允许先编辑，则重新校验并按新内容提交。超时后服务端是否已受理须由幂等/去重或查询能力处理，缺少该证据时不得宣称重试无重复风险。 | 重试后按实际成功、满额、明确拒绝或再次网络失败分支处理；仍失败时保留输入。 |

**产品状态约束：**活动身份贯穿详情、表单、提交和结果；未知结果不能转换为成功；网络失败不清空输入；满额与一般网络失败分开；每次请求结束后表单必须进入可理解的终态或可恢复态，不能永久停留在“提交中”。以上为建议提交给前端与 QA 的核心不变量。

| R1 活动列表 | 初次加载可理解；成功列表可选中活动；空、加载失败及手动重试各有明确状态。列表与详情身份保持一致。 | 有活动：选中第二项后进入第二项详情；零活动：显示空态而非错误；请求失败：显示错误并可重试，成功后恢复实际列表。 | 前端核实列表来源及活动身份字段；UI 定义列表、加载、空、错误及窄屏状态；QA 留下实际数据、操作和状态证据。 |

| R3 表单校验 | 已确认的必填、格式和长度限制有可见规则；失败定位字段、保留输入并阻止无效请求；修正后可提交。 | 对每个已确认约束覆盖一个非法值和一个边界合法值；留空、格式不符及超限均不发送报名；修正后仅发送一次有效请求；服务端字段错误仍保留其他输入。 | 产品需确认字段与业务约束，前端核实服务端校验契约，UI 定义错误关联和焦点；QA 用实际网络或请求记录证明无效输入未提交。字段未确认前不能宣布 R3 已具备实施前提。 |
| R4 名额满提示 | 详情可基于现有容量数据给出预提示；提交返回 `CAPACITY_FULL` 必须展示满额状态，不当作网络失败。前端不得自行决定增加名额。 | 已满活动显示满额且不能继续提交；起初有余量、提交返回 `CAPACITY_FULL` 时转入满额提示；原输入不被清空；可以返回列表。 | 前端核实 `capacity`、`confirmedCount` 的边界及 `CAPACITY_FULL` 响应形态；UI 定义满额文案/动作；QA 同时覆盖预判和提交竞争分支。当前已知 UI 缺口属于此项。 |
| R5 报名结果 | 明确成功与明确拒绝分开；成功关联当前活动；失败说明恢复动作；未知结果不伪装成明确成功或失败。 | 明确成功后出现成功结果并结束该次可提交表单；可修正错误回表单保留输入；权限/重复报名按实际响应语义呈现；成功文案、活动身份与响应一致。 | 前端核实成功最小证据、可用凭证及业务错误分类；QA 对照实际响应、可见结果及重复提交行为。没有成功响应证据不能判定 R5 成功路径通过。 |
| R6 网络失败重试并保留输入 | 网络失败及超时后不丢失字段，用户可主动重试；同一请求未结束时重复点击/回车不并发；重试结果仍按实际响应处理。 | 填入全部已确认字段并触发断网失败，核对每个字段仍在；网络恢复后主动重试，内容与活动不变，按响应显示结果；再次失败仍保留；模拟响应丢失后的重试以实际去重契约核对服务端效果。 | 前端定义保留范围、超时与重试、去重能力；UI 定义错误提示及恢复焦点；QA 记录失败注入方式、请求次数、提交内容、服务端实际结果与浏览器状态。幂等能力未知时只能给出部分证据，不能宣称重复风险已关闭。 |

手机触控、键盘和简洁清晰是跨 R1～R6 的共同验收约束：所有必需动作在窄屏可达，键盘可完成列表进入、填写、纠错、提交和恢复，焦点能定位当前错误或结果。具体视口、控件尺寸、焦点落点及辅助技术检查由 UI/QA 供稿确定；本岗位不另建平行尺寸标准。

| R6 提交网络失败 | 留在同一详情表单，显示“暂未确认报名结果，填写内容已保留。”，提供“重试”。如果适配层能证明未发送或明确失败，可使用对应更精确文案。 | 结束提交中状态，保留全部值及活动上下文；不要求重填，不自动导航，不自动连续提交。重试复用同次报名意图；安全重试与结果确认策略是前端/API 的前置契约，见第 7 节。 |

## 5. 手机、键盘、焦点与可访问性

- 窄屏以 320 CSS px 为检查起点，页面边距 16px，卡片与表单全宽单列，长标题、地点和错误文本自然折行；无水平滚动。正文缩放至 200% 时操作和错误仍可读可用；400% 缩放时按重排后的窄视口检查。
- 所有主要点击目标至少 44×44 CSS px，建议手机主按钮高 48px；相邻操作至少留 8px。只使用点击/键盘可达的操作，不以悬停、拖动或颜色作为唯一入口。
- 保持 DOM 顺序为返回导航、标题、活动信息、名额、字段、提交、反馈相关操作；Tab/Shift+Tab 可遍历所有交互元素，无正数 tabindex，不困住焦点。链接负责导航，按钮负责提交/重试；Enter 在表单内遵循提交校验和提交中防重规则。
- 键盘焦点采用清晰外框，建议 3px 主色轮廓并留 2px 间距；前端需检查实际背景下对比度和裁切。不得只靠背景色变化表示焦点，禁用态也要有可读文案和原因。
- 字段使用显式 label 与 id 关联，必填有文字/符号说明并与实际规则一致；错误用 `aria-invalid` 和 `aria-describedby` 对应。输入类型、autocomplete、inputmode 以实际字段确定；电话号码不以数值运算输入建模，不擅加固定地区规则。
- 表单校验失败聚焦带 `tabindex=-1` 的错误摘要；摘要及其相同文本不同时再次作为实时警报朗读。加载/重试进度用礼貌状态提示；未转移焦点的异步关键失败用一次警报播报，避免重复渲染反复播报。
- 路由视图切换后聚焦新页面 h1 并更新文档标题；同页提交失败只处理对应反馈焦点，不把用户送回页顶。正常输入时不因名额刷新、输入校验或 API 更新抢焦点。
- 对提交中保留在按钮上的焦点，采用原生禁用还是 `aria-disabled` 由前端结合现有组件确定；后者必须实际拦截鼠标与键盘执行，不能只改变视觉。禁用原因由邻近持久文字说明。
- 正文及关键状态文字目标对比度至少 4.5:1，大字至少 3:1；控件边界和焦点提示按相邻颜色检查至少 3:1。图标均有文字配合，纯装饰图标隐藏于辅助技术。

## 3. 数据与 API 假定契约

### 3.1 活动容量

**事实**只有字段名称和 `CAPACITY_FULL` 的存在。以下数值语义是待核对的设计建议：

| 数据或行为 | 建议约束及前端处理 |
| --- | --- |
| 活动标识 | 稳定且可唯一查询；实际字段名和类型待 API 确认，不以列表序号定位活动。 |
| `capacity` | 有限、非负整数，表示总名额。建议 `0` 表示无可报名名额；不得自行把 `0`、缺失或 `null` 解释为无限容量。是否存在不限额活动及其编码仍待确认。 |
| `confirmedCount` | 非负整数，表示已确认占用名额，实际计数范围待确认。 |
| 容量展示 | 合法快照下，`remaining = max(0, capacity - confirmedCount)`；`confirmedCount >= capacity` 为 `full`。计数暂时超过容量时不显示负数，重新读取并按满额处理。 |
| 无效或缺失快照 | `unknown`，保留其他可用活动信息并提供重新读取；建议在有效详情恢复前禁用报名，不伪造余量。实际兼容方案需结合现有 API 核对。 |
| 最终判断 | 服务端必须原子决定名额并返回报名结果；前端预检查仅改善反馈。两个客户端争抢最后一名额时，界面应能接收一个成功、另一个 `CAPACITY_FULL` 的结果。该并发保证尚未验证。 |

读取时已满则呈现满额提示和不可提交状态；提交时服务端返回 `CAPACITY_FULL`，即使刚才仍显示可报名，也立即呈现满额并保留所有字段。刷新详情确认最新计数；刷新失败不得清除已有满额结果或改回可报名。只有较新的有效服务端快照确认有名额后，才恢复报名入口。成功后读取服务端最新计数，不仅在本地执行 `confirmedCount + 1` 来冒充权威结果。

### 3.2 适配层接口与待确认能力

建议沿用现有适配层暴露列表读取、详情读取、提交报名、按请求标识核对结果四类操作。具体 HTTP 路径、方法、分页、字段名、时间格式与错误包结构未知；此处不指定虚构路由。任何新增服务端能力由主代理确认范围，不能写成已有实现。

| 操作 | 建议输入与输出 | 实施前必须核对 |
| --- | --- | --- |
| 读取列表 | 现有查询参数 → 活动集合及稳定标识；分页只在实际接口要求时处理。 | 实际查询方式、列表字段及空结果格式；标题等展示字段不能由本稿假定为已存在。 |
| 读取详情 | 活动标识 → 展示字段、`capacity`、`confirmedCount`。 | 活动不存在或已结束的错误；表单定义来源、详情与列表计数一致性。 |
| 提交报名 | 活动标识、已确认字段、逻辑请求标识 → 权威成功结果或可辨认错误。 | 实际响应中表示报名已成功的约定内容及其与本次请求的关联方式；`CAPACITY_FULL` 的响应包和无写入语义；字段错误、权限错误及其他业务拒绝。 |
| 核对结果 | 同一逻辑请求标识 → 成功、明确未受理/终态失败、处理中或未知。 | 是否已提供查询或等价的幂等重放能力，查询权限及“未找到”能否证明请求不会晚到。无此保证，不能把未找到视为安全重提。 |

成功判断以经核实的 API 响应契约及与本次请求关联的服务端结果为证据；不额外要求未经证实存在的独立报名凭据或编号。只展示契约确实返回的成功内容，个人信息范围由产品/API 确认。前端不把用户输入、脱离响应契约的 HTTP 2xx 或非预期响应包自行转换为成功；响应不足以按实际契约确认结果时进入安全核对。

建议适配层保留业务 `code`、字段错误、可显示的安全消息、请求追踪标识及“是否已确定无副作用”的判断来源。原始服务端内容按文本呈现，不作为 HTML；不记录报名个人信息或原始请求正文。无登录需求不代表接口无需权限约束，公开接口范围、跨域和已有凭据机制仍需核对，前端不得添加密钥或扩大访问。

### 3.3 重复提交与结果不确定

客户端在首次有效提交、进入异步调用前同步置为 `submitting`，统一拦截按钮、Enter 和重复事件。所有提交入口共用这个门禁；按钮禁用不足以代替处理函数检查。

建议服务端支持稳定的逻辑请求标识（幂等键或现有等价机制）：同键同内容返回同一逻辑结果，同键不同内容明确拒绝且不新增记录，并发同键不创建多条报名。只有在双方确认请求标识的传输位置、作用域、有效期和并发语义后，前端才能据此实现安全重放。单标签页的锁不能替代服务端防重；跨标签页、不同请求标识下相同报名人的重复报名规则也待产品/API 确认。

| 结果类别 | 下一状态与恢复操作 |
| --- | --- |
| 本地校验失败或调用前已阻止 | 没有发出请求，保留字段并修正错误；不产生服务器结果。 |
| 有经核实响应契约确认的成功结果 | `succeeded`，展示契约确实返回的结果信息，停止再次提交；输入转为结果上下文，不自动新建另一笔报名。 |
| 契约明确保证未创建记录的拒绝 | `failed`，保留字段，按错误修正或刷新；`CAPACITY_FULL` 同时置满额。允许新尝试前应满足相应恢复条件。权限拒绝不得无限重试或新增登录流程。 |
| 请求已开始后的网络断开、超时、取消，或不完整响应 | `uncertain`，保留冻结字段及原请求标识，明确“结果待核对”；不得声称失败且未报名。普通网络异常、HTTP 5xx 或本地取消本身都不能证明服务端没有写入。 |
| 结果未知时点击“重试” | 先进入 `verifying` 做安全核对，不直接新建报名请求。采用实际已确认的原意图查询、服务端去重或明确未提交证据；查询能力未知时不能假装调用。已成功转成功，仍处理中或未知则保留核对入口及不确定状态，不得以一次未找到代替终态保证。 |
| 核对后需要重放 | 只有可证明原请求未提交/未生效且不会再生效，或具备针对原意图的有效服务端去重保证时才允许发送。按实际契约重放原操作，保留同一请求标识及冻结字段，不得生成新标识盲重试。 |

已明确终结且无写入的失败后，用户修正字段可开始新的逻辑尝试；成功后不再提供重提。处于 `submitting / uncertain / verifying` 时建议冻结本次提交快照及直接重提入口，保留触发安全核对的“重试”操作；若允许编辑，必须保留原快照并先解决原操作，不能通过编辑绕过不确定结果。服务端去重与结果核对能力均未知时，普通失败反馈仍可设计，但 **R6 中结果不确定后的安全重试不能认定可实施完成**，须交主代理确认契约或明确未覆盖项。

## 4. 表单校验与输入保留

字段集合、必填性、长度、格式、重复报名身份规则尚未提供。product_owner 先确认业务要求，API 契约给出服务端约束，前端按同一规则实现；不把姓名、手机号或邮箱擅自写成必填项。

- 为每个确认后的字段定义类型、必填、长度和格式，以及对应字段错误；只做约定的规范化，不擅自转换大小写、删除字符或改写用户原始输入。
- 提交时校验全部字段；交互过程的校验时点按 ui_owner 规格实现。错误时保留值，先聚焦错误摘要，再由摘要链接定位首个或其他错误字段；服务端字段错误回填对应字段，未知字段错误放入表单级反馈，不能丢弃。
- 服务器仍校验全部输入。前端通过校验不保证服务器接受；业务拒绝、满额、权限错误、限流和网络不确定结果走不同状态，不能一律显示“重试”。限流等待规则以实际响应契约为准。
- 网络失败、服务端拒绝、核对中及详情刷新不清空输入。一次重试使用已冻结的提交内容；成功后仅按已确认产品流程离开草稿状态，不在错误路径复用清空逻辑。
- 本阶段 R6 保留保证限于当前表单内：校验失败、提交失败、名额满、重试和名额信息刷新均保留输入及当前活动上下文，不自动导航。切换活动后的旧响应不得覆盖当前表单，这不等于承诺离开路由后恢复草稿。
- 离开路由、刷新、关闭标签或浏览器重启后的恢复不是本阶段已确认范围，本稿不加入跨路由缓存或个人信息持久存储。未来若确认扩展，先确认保存期限、最小字段及隐私规则，再单独设计恢复；导航本身不证明服务端请求已取消。

## 5. 执行判定与证据门槛

- **未执行**：只有方法、没有本阶段实际操作；当前全部应用用例在此状态。**受阻**：明确缺少构建、环境、权限、测试数据或契约，列出受影响场景与责任人。**不适用**：最终确认范围/契约能证明场景不成立，写明依据，不用来隐藏必需目标缺口。
- **PASS**：该构建/该环境的前置、操作、全部预期和所需证据完整对应，且执行完整结束。**FAIL**：实际结果违背已确认预期，附最短复现、输入/响应、实际与期望、构建环境及影响 R；缺陷交主代理分配，不自行改实现。

| R6 结果未知 | 请求开始后的超时、断网、取消、5xx、响应解析失败不能直接证明服务端无写入。核查未知结果是否保留活动、原请求标识及冻结字段，是否会自动重试或产生新标识盲重提。取消前端等待不等于撤销服务端操作。 | 不确定错误到恢复入口的调用链；“服务端已写入但响应丢失”场景由 QA 取证，缺服务端证据不能宣称安全重试。 |
| R6 安全重试契约 | 只有原操作确定不会再生效，或存在有效的幂等重放保证，才能按契约重发。同一逻辑意图重放保持同标识同内容；同键不同内容、并发同键、有效期及查询“未找到”的语义以真实保证为准。编辑、切换活动或重新挂载不能绕过未决操作。 | 真实服务端契约、适配层实现与所有重试入口的对应关系；仅生成客户端标识、禁用按钮或一次查询未找到不足以证明去重。缺能力交主代理解决，审查岗不新增后台功能。 |
| 相关信任边界 | 仅检查本次链路涉及的响应形状校验、安全文本呈现、权限/错误处理及日志泄漏；不把“无登录”推断为可公开任意报名数据，不在前端新增密钥。 | 具体输入来源、渲染/日志/访问位置及可达影响；证据脱敏，不复制报名个人信息、令牌或完整原始正文。 |

## 5. 缺陷分级、证据格式与交接

以下分级为拟采用的报告约定，供整合确认；优先按可证明影响及触发面判断，不凭猜测提高严重性。

| 等级 | 判断方式与本项目相关示例 |
| --- | --- |
| P0 紧急 | 已证明影响广泛且正在造成严重数据破坏或敏感信息暴露，需要立即阻止相应交付；本稿不推断存在 P0。 |
| P1 高 | 关键报名流程在常见或明确可达条件下错误，例如确认后仍可重复创建报名、把未知结果显示为成功、错误报名到另一活动、泄露报名信息。须有对应调用链和契约证据。 |
| P2 中 | 特定恢复或边界分支损坏，例如 CAPACITY_FULL 未映射、失败清空字段、某一键盘入口绕过门禁；实际等级按影响与触发频度调整，不将示例机械定级。 |
| P3 低 | 不阻断主要流程且有局部影响的可证实问题；纯样式偏好、无影响重构建议不进入缺陷清单。可访问性缺陷按用户实际受阻程度分级，不能一律判低。 |

每条缺陷包含：简短标题与等级；目标差异身份；精确路径和最小相关行号；关联 R 编号与契约来源；前置状态及触发步骤；期望与实际行为；变更点→调用者→错误状态/副作用的证据；影响范围；现有验证能证明和不能证明的部分；建议修复位置及交接对象。建议修复位置不是本岗写入授权。静态推导须说明推导条件，未运行不写复现成功。

缺陷与其他事项分别报告：契约不明记“未决项”，无执行证据记“验证缺口”，技能依赖缺失记“审查阻塞”。未确认服务端幂等能力不能直接报“已存在重复报名缺陷”，但也不能将对应风险记已关闭。主代理接收缺陷并分配 frontend_owner 修复；delivery_qa 接收最小触发与预期，补实际行为证据；UI/产品接收规格疑问；本岗对新差异做受影响范围复核，不修改被审材料。

## 6. 依赖顺序、完成条件与未决项

1. 当前先完成方法供稿，由主代理整合。产品确认范围和字段；UI 明确交互与焦点；前端核实实际 API、容量、错误、成功及去重语义。各方共享定义由主代理归入新实施文档的唯一位置。
2. 主代理提供整合稿后，本岗只读复核：本方法的边界、前置、调用者覆盖、R4/R6 关键风险、缺陷证据及交接是否保留；是否把待确认建议、未执行检查或缺依赖改写为已完成事实。冲突返回主代理，不自行改共享文件。
3. 用户确认内容后，再由另起的实施任务开发。实现者提交实际差异和直接自测；QA 根据同一版本执行所需行为验收。本岗实际审查须先满足 Skill 依赖，审查与 QA 可复用有效证据，互不替代。
4. 后续实际审查完成条件：已授权范围及直接调用者覆盖；每项结论可追溯；已报告缺陷、验证缺口和阻塞；修复回到新差异按影响复核。没有未决问题不等于应用通过验收，最终交付由主代理决定。
