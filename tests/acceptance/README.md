# 隔离行为验收

`fixtures/` 是可重放的项目输入，`results/` 保存真实重放及后续定向复核的产物与证据。它们不是安装器、预置项目团队或用户项目的实施依据。测试中的用户回复是明确标注的模拟输入，不代表实际用户已经接受这些文档。

`npm test` 离线核对这些实际产物及当前 Skill/输入的 SHA-256，不启动模型、访问网络或修改用户配置。它会拦截陈旧证据、丢失供稿或复核、改坏的岗位正文、被覆盖的定制，以及越过内容确认的入口变更。它不能自行判断文档专业质量；该项由真实岗位贡献、专业复核和主代理验收负责，不靠回复关键词证明。

## 每次重放

1. 在系统临时目录创建全新工作区，将 `fixtures/team` 和 `fixtures/documents` 分别复制进去。不要在本项目、游戏项目或用户级配置中配置测试岗位，不覆写 `HOME` 或 `CODEX_HOME`。只有主代理写测试角色配置，子代理只能在独占的供稿/复核路径产出文本。
2. 读取当前 `agent-dispatch` 及参考文件，执行 `team/initial.md`。先保留完整方案，再提供明确标为模拟用户的方案确认，然后实际生成角色 TOML、协作规则和同提交许可。保存为 `results/team/initial/`。固定上游原件和许可在 `fixtures/team/upstream`，来源和原件哈希在 `source.json`，可联网核实固定提交，但不运行上游安装脚本。
3. 在生成的 Content Creator 中加入 `model = "gpt-6.1-sol"`、`model_reasoning_effort = "high"`，以及“用户定制：本项目审稿”的职责补充，保存完整 `before-addition/` 快照。执行 `team/addition.md`，核对旧团队后展示并确认增岗方案，实际应用并保存 `after-addition/`。用可用 TOML 解析器解析输出，再逐字比较原岗正文、原配置与许可。没有解析器时记录 PARTIAL，不能把快照字符串检查当成原生 TOML 解析。
4. 在同一配置上向新的独立代理显式使用 Skill，重放 `team/repeat.md`。可提出真实缺口，不提前告知预期选岗结论；代理不得写配置。主代理记录请求前后全树哈希及代理结论到 `results/repeat.json`。没有改动才是幂等通过，单独调用文件生成脚本两次不算。
5. 读取当前 `agent-dispatch-doc` 与参考文件，执行 `documents/request.md`。展示并保存完整文件方案，再输入模拟方案确认。主代理为共享文档唯一写入者，按 fixture 中五个实际岗位定义逐个委派专业供稿；每岗独占 `contributions/<role>.md`，不可递归委派。UI 设计实际读取并使用 fixture 的 `visual-layout`；审查岗位只编写检查方法，不因 `defect-evidence` 缺失阻断全部文档。
6. 整合真实供稿成 `docs/implementation.md`，另写 `docs/README.md` 草案索引。每岗读取整合版，只读复核其专业范围，并输出独占的 `reviews/<role>.md`。修正实际冲突后让受影响岗位复核。验证 R1～R6 流程、容量满、失败保留输入、接口/状态/未知项、每岗具体工作和可执行验收方法；旧 React、清空输入及 PASS 不能被继承。没有实际项目执行记录时仍为 NOT_RUN。
7. 专业复核完成但尚无内容确认时，保存 `results/documents/`，必须为 DRAFT，原岗位、技能绑定、旧文件及 `AGENTS.md` 不变。随后在另一个隔离副本中给出明确标注的**模拟内容确认**，才将新文档升级为实施依据并更新已约定的入口；保留旧文件为历史，保存 `results/promoted/`。这只验证批准后的状态迁移，不批准真实用户项目文档。
8. 保存真实调用身份、方案/模拟决定、贡献与复核路径/哈希、TOML 解析器和检查结论、未覆盖项到 `results/replay.json`；记录重放所用版本、完整 `skills/` 与 `fixtures/` 文件哈希。路径均相对本测试目录，不能留下临时目录依赖。运行 `npm test`，再独立审阅行为证据和实际文档，不能为了使测试通过把未参与或未执行项改为 PASS。
9. 修改协作与验收规则时，使用 `fixtures/delivery-controls.md` 在新上下文中重放，保存原始方案和人工核对记录到 `results/controls/`；核对检查强度、缺口返回、返工结束、版本失效与契约接缝，不能用 Skill 中包含某个关键词证明行为通过。保留基线缺少的行为及已有正确行为，不把单次重放称为统计改善。
10. 修改项目学习时，按 `fixtures/learning/request.md` 在临时项目生成真实入口、协议与记忆。真实 Content Creator 读取生成配置，修正稿件并交接增量；主代理核对依据、写前版本、原始增量 SHA-256，保存完整结果再整体回读。随后以全新上下文派发同岗另一活动任务，提示中不提供待验证答案；检查其实际读取和稿件。等价任务无新增认识时，记忆、回执及修订不得变化。保存原始派发、报告、增量、项目产物及身份到 `results/learning/`。
11. 使用 `learning/boundaries.md` 构造独立原始输入，实际读取协议判断候选、缺文件、失败归因、权限、来源变化、多实例/重试/冲突、单写者、中断、归档、只读、生命周期、结束条件与文档独立安装。中断用人工预置不完整状态核对恢复决策，不称为真实进程崩溃测试。只读项目使用全树前后哈希证明未写；声明了精确保存例外的情景只验证授权判断，不冒充完成了保存。
12. 路径与安全保存修复使用 `learning/review-fixes.md`。独立代理读取当前 Skill 输出实际映射及保存代码，主代理在临时项目生成配置并解析；对该代码在隔离子进程注入暂存部分写入、替换前和替换后的终止，保存退出码及实际目标/暂存字节。正常保存、首次创建、归档、缺授权、残留暂存、陈旧版本、链接别名、替换或同步失败分别检验。原始产物、可重放的标准库故障注入脚本和实际快照保存在 `results/learning/fixes/`；这些代码是验收产物，不安装为项目运行引擎。原有预置状态报告保持历史范围，不改写为动态通过。需要重新执行进程验收时，在新的临时目录复制 `saving-input/`，运行 `python3 -B fault-harness.py <临时目录> <save-memory.py 路径>`；不要覆盖保存的证据。`npm test` 仍只离线核对证据，不要求 Python 或调用模型。
13. 补充恢复验收时，运行 `python3 -B tests/acceptance/recovery-harness.py <新建的空临时目录> <results/learning/fixes 的绝对路径>`。脚本重放上述真实中断，再将其残留逐字复制给新进程，执行恢复、重复提交与只读接手；另从非空归档执行两步迁移，在五个提交边界注入中断或失败，再恢复并重试。目标及清理暂存的授权均为隔离模拟，暂存需匹配实际观察指纹和候选，未知残留不能套用清理。保存原始输入、请求、各阶段完整快照、进程结果和代码指纹到 `results/learning/recovery/`。这是进程级的存储与协调验收，不是新模型上下文自主恢复、断电或跨文件事务验证；真实项目仍按项目协议由主代理处理。

定向变更可以保留仍适用的历史供稿与专业复核：在 `replay.json` 保留原调用身份、原执行时间及原始 Skill 哈希，另记当前定向重放/复核的范围、时间和依据，多轮定向验证保留各轮来源。受影响流程必须重跑，不能仅更新哈希冒充运行。学习首轮重放团队配置、增岗、幂等和学习链路；路径修复轮重放路径配置、安全保存及更新协议后的幂等；恢复补充轮执行真实残留接手、重试、只读和两步归档。既有五岗文档内容、输入、整合稿及批准对象不变，原纠错/复用记忆也未改写，因此保留原始证据及其适用范围。离线断言只核对保存的真实产物和人工复核记录，不自动执行模型或证明长期效果。

快照只排除 Finder `.DS_Store` 元数据，其余输入及产物仍完整核对。

## 超时回归

修改恢复脚本的进程管理时，显式运行 `python3 -B tests/acceptance/test_recovery_timeout.py --report <临时目录中的报告路径>`。该标准库回归调用真实 `invoke()`，用真实子进程输出看似成功的 JSON 后挂起；测试将通信超时缩至 0.05 秒，检查超时会终止并回收子进程、保留完整输出并继续抛出异常。子进程最多自行等待 2 秒，使旧实现也能有限时间失败。修改前后报告及原脚本保留在 `results/learning/recovery/timeout/`。恢复脚本指纹变化后，仍需在新空临时目录重跑完整恢复验收并保存实际产物。`npm test` 只核对已保存的报告与源码指纹，不运行该 Python 测试。

## 比较规则改动

复用这些输入和已有用例，不另建评估系统。修改前后固定相同任务、fixture、模型、effort、工具和环境；采用全新上下文并交替运行，正式效果比较每侧至少三次，报告样本数。评分依据实际产物、差异和执行记录，预期判定不交给执行代理。检查选岗复用、重复提问、定制与边界保留、下游可执行性及无依据的完成声明，再比较耗时与运行时报告的用量；未知用量记未知，不用阅读字数代替 Token。静态测试和单次行为样本只报告其实际覆盖，不据此声称节省成本或某模型更优。

## 判定标准

| 场景 | 必须从实际文件核对的结果 |
| --- | --- |
| 首次配置 | 非软件项目目标和完成标准明确；采用必要上游岗位；原名/描述/完整正文、固定来源与完整许可可追溯；没有内容制作或实施文档越界。 |
| 真正增岗 | 先核对已存在的实际职责；新增专业责任有缺口依据；原模型、定制与内容全部保留；交接清楚，许可复用。 |
| 重复调用 | 新独立代理基于实际项目判断复用；前后所有配置字节一致，没有重复岗位、规则或许可。 |
| 团队文档 | 五岗都有可定位的专业工作、输入输出、依赖和完成条件；都有实际供稿与整合版复核；技术/交互/验收一致，引用可用，不依赖旧设计。 |
| 协作与验收约定 | 按实际变更影响选择检查强度；通过、缺陷和缺条件分别返回；第三次非阻塞返工不扩大范围；版本变化后检查失效结论与上下游接缝，环境不足不冒充应用通过。 |
| 确认门槛 | 方案确认不等于内容确认；专业复核后仍是草案，未经内容确认不改实施入口；模拟内容确认后才能升级，实际开发仍未运行。 |

本组用例刻意不覆盖所有项目类型、宿主版本、网络故障和真实法律/发布工作；没有证据的能力不得从这些测试外推。
