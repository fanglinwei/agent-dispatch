# Codex 项目岗位配置

配置前核对当前宿主支持的格式与已有配置。以下结构已于 2026-10-17 对照 [Codex 自定义岗位文档](https://developers.openai.com/codex/subagents/) 和 [上游 Codex 集成](https://github.com/msitarzewski/agency-agents/blob/main/integrations/codex/README.md) 核实；版本差异以当前证据为准。

## 上游与来源

通过网页、可用的只读 API 或已有本地副本查阅 [agency-agents](https://github.com/msitarzewski/agency-agents)。先定位候选，再读取实际正文与同一提交的许可；不要只凭岗位名或搜索摘要生成岗位。把选中内容固定到具体提交，后续更新只在本次需求需要时提出，不自动覆盖本地改动。

每个生成的角色文件以 TOML 注释记录：原岗位名、原文件的固定提交链接、许可位置，以及“仅格式转换”或实际适配说明。复制上游正文时把该快照的完整许可及版权声明保存在 `.codex/agents/LICENSE.agency-agents`，已有同一声明则复用；已有不同版本声明时保留并补充所用快照，不覆盖旧许可。许可是集成所需文件，即使用户不输出项目文档也保留。

优先保持上游 `name`、`description` 和专业正文。源 Markdown 的展示元数据不转换成 Codex 配置项。仅在名称冲突、宿主工具差异或与本项目明确规则冲突等确有需要时做最小适配，展示差异。不能通过保留不适用的上游工具名或外部操作要求来扩大岗位权限。

## 文件结构与格式

项目级岗位放在 `<项目根>/.codex/agents/<安全文件名>.toml`，每个文件一个岗位。当前格式要求三个非空字符串：`name`、`description`、`developer_instructions`。例如，以下仅示意结构，生成时填入所选原岗位的实际内容：

```toml
# Source: 固定提交的原文件链接
# Adaptation: 保留上游完整正文，追加项目学习入口（以实际适配为准）
# License: 见 LICENSE.agency-agents
name = "所选上游原岗位名"
description = "所选上游原描述"
developer_instructions = '''
所选上游岗位的完整专业正文。
配置学习时追加的简短项目指引。
'''
```

角色按 `name` 识别，文件名只负责安全存储。检查已有项目岗位、可见用户级岗位与内置岗位的名称；发生冲突时复用已有适用角色，或在方案中给出唯一项目名并保留上游原名记录，避免无意遮蔽角色。

转换时使用可靠 TOML 序列化或选择能完整容纳原文的字符串形式，随后解析并逐字核对正文；注意 Markdown 中可能有引号、反斜杠和多行定界符。若实际做了已确认的适配，核对的是适配后的预期正文。

项目学习属于必要适配：按 [项目岗位学习配置](project-learning.md) 保留全部原文并追加项目入口、稳定标识及记忆指引，记录实际差异；不新增未经支持的 TOML 字段。

原生项目目录加载可用时，不为注册岗位额外创建 `.codex/config.toml`。已有其他注册机制或旧版本时，核对实际支持后仅修改方案中已确认的必要项；没有证据时标注加载待验证，不猜写配置键。

新岗位默认省略模型与 effort，遵守目标环境现有模型选择规则。已有岗位的模型设置和用户定制保持不变，发现与目标规则冲突时报告并纳入方案。省略字段不证明实际运行模型；需要选择模型时核对宿主默认、角色覆盖和可用性。

## 项目 AGENTS.md

先读完整适用规则和已有协作区块。有现成岗位表与边界时在原处更新，保留其格式和标记；没有时增加一个集中协作区块，不复制整份现有规则。遵循已有规则的权威顺序，不用新段落覆盖用户的权限约束。

配置内容包括简短目标与完成标准、岗位调用表、成果主责及交接、主代理保留职责、具体派发契约和授权边界。项目分工收窄本次责任，岗位原有专业能力仍可用于其授权任务。每个共享成果和共享文件指定唯一写入者，其他岗位提供意见或输入。

按 [岗位与 Skill 使用规则](role-skills.md) 集中记录岗位、任务触发条件、Skill 名称与已核实位置、使用要求及缺失处理；每次派发携带适用项。优先用项目规则落实，不为绑定技能大改上游专业正文。Codex 子代理继承父代理的 Skills，`skills.config` 可用于禁用技能；可用性配置不等于必用约定，不猜写 `skills = [...]` 等未经支持的配置键。

在协作规则中写明主代理可按任务需要调用已配置岗位，并继续遵守适用委派与权限限制；不把它扩张为自动开发、外部通信、发布或 Git 写操作授权。若规则明确禁止子代理修改代理配置，由主代理完成本次配置文件写入。

按 [项目岗位学习配置](project-learning.md) 在同一入口记录学习协议、每岗稳定映射与精确读写范围，检查所有输出路径无冲突，明确目标及其同目录暂存的授权；将协议复制到项目，日常任务不依赖 Skill 的安装目录。每次派发携带项目根、岗位/任务/实例标识、相关记忆及读入版本和原验收状态；学习不改变风险、两轮返工或授权规则。

实施文档的默认维护责任可作为选岗和分工依据，但具体编写交给用户显式调用的 `agent-dispatch-doc`；本轮不生成额外需求、设计或进度文档，也不依赖文档 Skill 的目录文件。交接已确认目标、角色职责、Skill 规则与未决项即可。

## 协作与验收约定

把下列约定按项目实际成果写入已有协作区块；已有等效规则时沿用，不另设台账或为了检查固定增加岗位。这里只配置后续执行的方法，不运行项目验收。

- 按变更范围与风险安排检查：`light` 用于单一主责且不改变共享契约、权限、数据、基础设施或依赖的局部工作，一次针对性验证即可；`standard` 用于其他常规交付，安排结果符合性验证和专业质量复核；`high` 用于支付、权限、敏感资料、数据迁移或删除、生产基础设施等高风险变更，明确安全边界，并在运行条件允许时采用独立验证与复核。具体等级与理由随任务确定，不按岗位名称定级。非软件项目按成果正确性、授权和不可逆影响适配。
- 说明谁验证结果、谁复核质量，以及失败交回谁修复。通过与未通过分别记录；缺环境、缺材料或缺授权要指出具体缺口和恢复条件，不能当作产品缺陷或通过。可采用 `PASS / FAIL / NEEDS_ENVIRONMENT` 与 `APPROVE / CHANGES_REQUESTED / NEEDS_EVIDENCE`，或保留项目已有的等效结论。自查、同一会话的不同检查与独立岗位检查分别说明；明确要求的独立检查不可用时，受影响部分为 `PARTIAL`。
- 每次交接标明实际产物路径及版本或内容哈希、验收标准、检查范围、已执行方法与结果、未覆盖项。包含未提交修改时，仅分支名或提交号不足以定位对象。变更后由原检查者核对影响，只复核失效的结论和相邻影响；未变且仍适用的证据保留。
- 阻塞缺陷汇总后交回原负责人，建议与风险提示单列。同一验收单元默认最多两轮合并返工；仍有阻塞时交主代理裁决或向用户提出选项，受影响部分保持未完成，不自动追加修复循环。通过后的非阻塞建议留给用户选择；新缺陷或用户新增要求才重新打开相应范围。
- 集成检查实际产物的输入输出对应，例如接口字段与消费端、资源规格与接入方、内容来源与引用、规则与验收用例。各岗分别通过不能代替跨岗契约检查。

## 最小充分验证

- 用可用的 TOML 解析器（例如 Python 3.11+ 的 `tomllib`）解析新增或修改的角色文件，核对三个字段为非空字符串、名称唯一、相对引用存在，正文转换没有丢失内容。解析器缺失时报告格式验证未完成，不能凭目视声称通过。
- 检查本次精确文件差异：已有用户内容保留、角色来源可追溯、许可完整、主责与交接一致、主要交付目标有覆盖。没有 Git 时直接比对改前快照与改后文件，不初始化 Git。
- 核对 Skill 的真实指令、定位方式、触发范围与依赖；没有把“启用”当成“已使用”，缺失必用能力的任务没有被报告为完整成功。文档涉及的责任变更明确交接给后续文档任务，不在本轮声称完成团队文档。
- 再检查一次现有结果，确认同样需求不会重复创建岗位、协作区块或许可副本。
- 如果可以只读列出宿主实际注册的岗位，用列出结果核对；否则将加载状态留为未验证，提示新建会话或重启后核对。不要通过试派发来启动项目工作。按环境授权需要时，可由主代理读取角色职责交给通用委派工具，但应注明这不证明原生加载成功。

返回文件路径、保留/调整/新增岗位及原岗来源、职责交接、校验结果和未覆盖项。配置写入、格式有效、宿主已加载是三种不同证据；只声明实际验证过的结果。
