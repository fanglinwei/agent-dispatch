# 需求访谈

访谈的目的，是尽量理解使用者的需求与目标，让选岗和交付标准有依据。使用用户的语言，按实际项目追问，不把不适用的维度变成必答题。

## 按需求选择访谈能力

用户明确指定时优先采用其选择；未指定时按本轮需要判断，不要求用户先选工具：

| 本轮需要 | 采用方式 |
| --- | --- |
| 推敲构想、功能、流程或方案，暴露遗漏、隐含假设与边界，无需同步维护领域记录；不要求有代码仓库 | `grill-me`，解析并执行其实际依赖 `grilling`。 |
| 在已有项目中新增或调整功能，需对齐业务术语、概念关系与现有实现，并持续保留领域认识或重要决策依据 | `grill-with-docs`，解析并执行其实际依赖 `grilling` 与 `domain-modeling`。术语表按需维护，ADR 按实际决策判断。 |
| 需求已充分明确，或局部增岗仅余少量决定 | 复用已确认结论，只问影响本次配置的未知项；没有未知项就进入方案确认。 |

从当前技能目录或已知安装位置核实所选入口及其依赖的真实 `SKILL.md`，接受宿主实际注册的限定名称，不固定插件版本或本机绝对路径。按实际正文解析依赖，不只凭入口名称判断行为。宿主有 Skill 工具时按其要求调用；没有时读取入口、依赖及本次需要的格式参考后执行，不声称发生了工具调用。遵守显式调用限制；用户明确要求本流程按需使用这些入口时沿用该授权，仅安装或可见不等于允许调用。

两者共用 `grilling` 的决定树与分轮追问；`grill-with-docs` 额外主动澄清领域模型，并非只是把问答保存成文档。不是所有已有项目或技术问题都需要它；普通功能取舍且无领域建模需求时仍用 `grill-me`。开始时简述选择及理由。普通访谈中出现领域建模或记录需求时，可切换到 `grill-with-docs`；已有记录足够、后续只需澄清时可使用 `grill-me`。两者共享同一决定树和已确认答案，不并行开展两套访谈，不因切换重问已解决的问题。

推荐入口缺失但依赖可用时，可直接按依赖的方法继续，并说明实际采用方式；依赖缺失时，仅对可执行部分使用已读取的方法，其余采用下述分轮方法。说明缺失与未完成范围，不声称完整执行所选 Skill，不自动安装插件。用户或项目明确要求某 Skill 必用且不可替代时，按岗位与 Skill 使用规则将依赖部分标为 `PARTIAL`，其他独立工作继续。按需使用宿主的问题工具或普通对话。

## 术语表与决策记录

采用 `grill-with-docs` 时，先核对已有 `GLOSSARY.md`、`GLOSSARY-MAP.md`、ADR 及项目文档约定，复用实际位置，避免另建平行记录。发现用户用语与既有定义冲突时立即指出；对含混或重载的词提出精确定义，用具体业务场景检验概念关系与边界。用户描述涉及现有行为时查证实现；若不一致，区分当前事实与期望变更，再由用户确认取舍，不擅自以任一方覆盖另一方。术语表只记录已澄清的领域概念，不混入实现细节、需求清单或岗位配置。只有决策难以逆转、缺少背景会令读者困惑，且确有取舍时才提出 ADR；普通决定不逐条建档。文件在有实际内容时才创建，使用 `domain-modeling` 的格式参考。

将访谈记录的精确写入路径和拟记录内容纳入授权范围；已有明确授权时，术语确认后及时更新，ADR 按依赖方法提出并获准后写入。授权不足时先在对话中保留已确认条目与待写内容，随配置方案展示后等待确认，不因“边访谈边记录”提前写文件。没有适用内容就不建空文件。未确认的概念、取舍或建议不写成既定决定。

术语表和 ADR 是需求确认的记录；完整需求、技术设计、实施计划等项目实施文档仍交给显式调用的 `agent-dispatch-doc`。交接时引用已有记录、维护责任和待确认项，不重复生成另一套文档，也不要求为这两类记录另设岗位。

## 分轮方法

1. 用已有材料和对话建立决定树：哪些决定已确认，哪些未知，哪些依赖其他决定。
2. 每轮询问当前前置条件已明确、确实影响配置的未知决定；把依赖本轮答案的问题留到下一轮。
3. 问题编号，说明为何需要这个决定，并给出一个推荐答案及简短理由。措辞让用户回答“是”即可接受推荐，也允许用户直接改写。
4. 等待回答后更新理解；对含混或矛盾的关键点追问，其余继续。用户委托判断的事项可以自行选择，但标为代理建议或判断，不能写成用户原话。
5. 当用户对目标、完成标准、约束、岗位与 Skill 使用方案形成共同理解时结束。已确认的完整方案可直接执行；普通需求回答或沉默不等于对未展示文件变更的确认。实施文档需求作为选岗和后续交接资料，具体编写由用户显式调用 `agent-dispatch-doc` 推进。

每轮只提出有依赖依据的问题，避免为了填表询问用户能从环境直接查到的事实。后续增设以需求变化和能力缺口为起点，已有结论仍有效时直接引用。

## 按需覆盖的维度

| 维度 | 需要澄清的决定 |
| --- | --- |
| 项目与受众 | 要解决什么问题，为谁完成什么成果，成功后能做什么。 |
| 核心工作与流程 | 必须具备的功能或工作、优先级、从开始到交付的完整流程、关键边界与异常场景、明确不做的范围。 |
| 现状与约束 | 已有成果、当前阻塞、人员或资源、时间与成本、数据或内容来源、不能改变的约束。 |
| 技术与工具 | 适用的平台、技术栈、工具、集成及交付载体；区分用户已定、环境事实与待建议选项。 |
| 设计与表达 | 有视觉或内容体验要求时，核对参考、风格、品牌、交互、语言与受众体验。 |
| 交付程度 | 本阶段要做到什么程度、交付什么、谁验收、用哪些证据证明完成；有发布需求时核对发布条件。 |
| 协作与技能 | 现有岗位及权责限制、需要补的能力；用户指定的 Skills、按任务触发的必用或推荐要求。可用性与依赖从环境核对。 |
| 后续文档责任 | 文档是否属于交付目标、需要哪些专业岗位及维护主责；本轮不展开文档编写方案。 |

“原型”“MVP”“完整产品”等软件标签只在适用时使用。其他项目用其实际成果和验收证据定义完成程度。用户只要求局部增设时，不重新访谈所有维度。
