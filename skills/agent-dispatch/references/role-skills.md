# 岗位与 Skill 使用规则

岗位定义谁负责，项目实施文档定义本项目要做的具体工作，Skill 定义适用任务的工作方法。岗位名不能代替任务判断；代理能看到某个 Skill，也不能证明它已经使用。

## 配置时查证与选择

先读取项目已有要求和用户指定项，再从当前环境的技能目录或已知位置查找相关 Skills，读取候选的真实 `SKILL.md` 及其必需依赖。核对适用平台、任务、权限、调用限制和实际可定位路径；不照搬本机路径，不把未安装的推荐项写成可用技能。

用户指定优先，项目强制规则继续适用；对尚未指定的任务，按需要提出最少的技能建议。检查已有绑定，复用仍有效的项目选择，不因新一轮选岗覆盖它们。技能引入需要的安装、外部服务或付费不由岗位配置自动授权。

每条使用规则应包含：

| 项目 | 记录内容 |
| --- | --- |
| 岗位与任务 | 岗位身份，以及能观察到的具体触发条件；避免“这个岗位所有任务都用”。 |
| Skill 与位置 | 实际名称及已核实的路径或宿主定位方式；同名项须明确采用哪一份。 |
| 使用要求 | 触发后必用，或按需推荐；用户明确指定为必用的不得自行降为推荐。 |
| 依赖与不可用处理 | 已知必需依赖及当前状态，受影响的任务，允许的后续处理。 |

这些规则纳入完整岗位方案一起确认。Skill 本身的使用范围和调用策略仍有效；项目绑定不能绕过仅限用户显式调用的限制，已有明确授权则沿用，不重复索要。

## 持久记录与实际派发

项目 `AGENTS.md` 的协作区块是岗位与 Skill 使用关系的集中入口；已有等效的权威规则文件时保留它并从入口引用，避免并行维护多份表。实施文档可引用该规则，详细描述各岗位的项目工作，不复制整份 Skill 正文。

尽量保持上游角色原文。确需在角色 `developer_instructions` 中增加提示时，只增加读取项目规则并按任务遵守技能要求的简短指引，记录适配差异，不重复整张绑定表。无需为技能使用创建新角色或未经支持的 TOML 字段。原生继承、启用或禁用只说明可用性；必用要求通过指令与派发落实。

主代理每次派发，在原有目标、资料、精确读写范围与验收要求中，加上本次适用的 Skill 名称及已核实位置。岗位代理开始相应工作前读取真实指令，按要求调用或执行适用步骤，并核对其必需依赖；没有专用调用工具时，遵循该 Skill 允许的读取执行方式，如无允许的方式则报告受限，不假装调用。

例如，UI 岗位承担浏览器页面视觉设计时，可按已确认规则使用 `frontend-design`，交付布局、组件、交互状态及交接规格。仅交付方案时不因此启动页面开发。代码审查岗位执行实际代码审查时使用 `code-review` 及其要求的依赖；该岗位编写审查方法或检查设计文档时，不仅凭岗位名触发代码审查。目标环境没有这些技能时，按实际目录重新选择或报告缺失。

## 冲突、缺失与返回证据

- 技能指令不扩大本次任务、岗位写权限或外部动作授权；冲突按适用规则的权威顺序处理，无法兼容时报告受影响部分。
- 必用 Skill 或其必需依赖不可用时，暂停依赖它的任务并标为 `PARTIAL`，说明缺失与恢复条件；其他独立任务继续。不擅自安装、替换或跳过必需流程。推荐项不可用时可说明后采用适用的一般方法，不声称使用了该技能。
- 交付时简述实际使用的 Skill 和对应产出；区分可用、已读取、已用于任务、执行受阻，不为证明“使用”另造冗余日志，也不把读过说明当成完成了技能步骤。
- 后续增岗或职责调整时，只复查受影响的任务、技能规则与依赖，保留未受影响的用户选择。环境或技能变更后重新核对相关路径与要求。
