# 由配置后的团队编写新的实施文档

在显式调用 `agent-dispatch-doc` 时使用。文档是后续各岗位开展项目工作的共同实施依据，必须先核对团队配置；已有岗位适合时复用，确有缺口则交回 `agent-dispatch` 的配置流程。本 Skill 不增岗，不以文档任务跳过团队前置条件，也不要求另一个 Skill 同时安装才能使用已有团队。

## 新文档的依据与状态

以最新用户目标、约束、实际项目事实和团队专业设计为依据，形成可独立阅读的新文档或文件集。旧文档仅供必要背景查证；需要采用的结论重新核对后写全，避免用“同旧文档”代替规则、接口或工作说明。不自动继承旧文档的权威、进度和验收结论，也不自动删除或覆盖旧文件。

方案中确定新文档的精确路径和单一入口。首次形成的内容标为 `DRAFT`，区分已核实事实、已确认要求、团队设计建议及待决定项；重要未知影响实施时交用户澄清。每项已有成果或执行结论有实际证据，计划、文档完成与功能完成分别记录。

用户确认文件方案后才编写；内容完成并经专业复核后，再请用户确认新文档成为实施依据。文件方案获批不等于接受尚未形成的设计。草案可被引用，但不能被标成已确认基线。

## 先配置，再按岗位实际产出

1. 主代理核对已配置岗位、协作及 Skill 规则与其现有证据。既有团队适合时记录核对结果，不制造配置改动；发现缺口交回团队配置。尚不能原生调用的岗位，在环境允许时由主代理通过通用委派携带已读取的实际职责；注明这不证明原生加载成功。
2. 首次完整文档把每个岗位映射到本项目的具体工作及对应文档，每岗至少实际贡献自己的领域设计、实施安排或专业复核方法；后续局部维护仅调用受影响岗位。仅承担后续实现、审查或测试的岗位，也应具体定义自己的方案、检查点、输入输出及完成条件，不能只列岗位简介。
3. 每份共享文档指定唯一写入者，其他岗位供稿或复核；按依赖安排贡献，独立输入才并行，不要求所有岗位两两互审。派发具体目标、资料、Skill、允许动作、精确读写路径、交接和验收，默认维护负责人不等于整目录写权限。
4. 文档负责人整合已提供的专业内容，主代理处理范围与跨岗契约冲突。各专业岗位复核受其负责范围影响的整合结果；用供稿或复核结果记录实际参与，主代理不替专业岗位虚构结论。

岗位调用、模型选择和写入权限遵守环境规则；代理配置由允许的主责写入者完成，不能以编写文档授权绕过配置限制。若不能实际调用所需岗位，可以完成不受阻的草案或准备，但团队共同产出要求标为 `PARTIAL`，说明未参与岗位与未覆盖内容，不把主代理独写声称为全团队交付。

## 项目学习的读取与交接

项目 `AGENTS.md` 或其权威协作文件已有学习入口时，读取其项目内协议和岗位映射；每岗任务开始前实际读取相关记忆并核对来源适用性。派发携带项目根、稳定 `role-key`、协议/记忆路径、读入修订（未知先读取）、任务与实际实例标识、本次授权及原返工状态。执行中失败或收到纠正就核实、修正、针对性验证；完成时简短复盘，有可复用增量才交接。阶段保存不新增学习触发，反思不重置既有返工计数。

角色只写任务独占产物，不改共享记忆或角色配置。主代理遵守项目协议的单写者、版本比对、去重、安全保存和完整回读，并先核对本次权限：只读审查默认只返回待保存增量，日常维护授权不能覆盖本次只读限制；有明确适用的精确保存例外时仅写其路径。普通可写文档任务沿用项目已获日常维护授权，不重复确认；安全保存所需的目标及同目录暂存路径都须在授权内，缺少时保持待保存，不改为原地覆盖。方案需列出本次实际涉及的路径，不将文档入口权限扩张为协议或岗位配置修改权限。

新事实、候选设计、已确认要求分别记录。文件方案批准及专业复核通过都不等于用户确认最终内容；只有对应版本的真实内容确认才能支持已确认决定。环境或授权缺口不记作角色能力缺陷；无新增认识不制造条目。任务结果、增量保存与条目有效性分别报告，待保存/候选不单独使已完成文档失败。

记忆缺失或冲突时，依当前权威资料继续可完成部分，报告缺口或将受影响结论交主代理核对，不声称已加载、不在本流程补建学习配置。已有等效项目协议按实际路径沿用；普通任务不读取另一 Skill 的私有目录。需迁移、改名、替换或重分职责时交正式团队配置入口，本 Skill 继续不受阻文档部分。

## 工作内容与颗粒度

参考三国霸业文档中产品、规则、技术、UI/美术、进度和测试的细化程度，采用“可执行、可交接、可核验”的标准；不复制其游戏内容，也不强制所有项目分成六份文档。按项目领域组织，一份文档可以覆盖多个领域，但所有岗位的实际工作要有清晰定位。

每个岗位的工作记录至少包括：本项目责任与边界、具体工作或设计、输入与前置条件、输出与交接对象、依赖及顺序、验收方法与证据要求、已确认决定及未决项。仅写“负责 UI”“保证质量”等职责口号不足以指导实施。

以下是软件项目中可检查的深度；其他项目按自己的内容规范、生产环节、交付载体和检查方法表达同等细节，跳过不适用项。

| 领域 | 至少细化到可执行的内容 |
| --- | --- |
| 目标与端到端流程 | 受众、范围与排除项、优先级、完整使用或交付流程、分支与恢复、完成标准及需求到验收的对应。 |
| 领域规则与内容 | 操作或生产步骤、输入与效果、数值或格式要求、顺序、合法性、取消/拒绝/边界；适用时给出可核对示例。 |
| 技术与生产方案 | 模块或环节的主责、接口和数据/内容契约、状态变化、集成、兼容、存储、构建或生产方式、失败处理与交接。 |
| 交互与视觉/表达 | 信息层级、页面或载体、组件、完整状态、布局及平台约束、可访问性、素材规格、资源交接和符合性检查。 |
| 实施与协作 | 任务主责、依赖、阶段入口与出口、交接物、阻塞、维护责任和后续更新方式；执行状态只按证据记载。 |
| 审查与验收 | 审查范围与方法；测试或检查的前置条件、输入/操作、预期、边界及失败复现、通过标准、证据和未覆盖范围。 |

同一规则、接口或状态由一个位置定义，其他文档引用新文件中的该定义；确认输入输出与各岗交接一致。复用项目已有的需求、任务和用例编号，不另建平行台账。尚未执行的检查标为未执行，不为了“文档完整”填写通过结论。

## 验收安排与复核结论

沿用项目已有的协作与验收规则；缺少时，在本次文档方案和实施安排中补足以下内容，不反向修改岗位配置或 Skill 绑定。本次文档检查和未来项目验收分别说明对象与强度：写出检查方法不代表已执行检查，未来浏览器或生产环境缺失不阻断不依赖它的文档工作。

| 级别 | 判断依据 | 检查安排 |
| --- | --- | --- |
| `light` | 单一主责，局部修改，不改变共享契约、权限、数据、基础设施或依赖 | 针对性检查即可，不固定召集全团队；首次完整文档仍须满足全部岗位实际参与的要求。 |
| `standard` | 其他常规交付，例如跨岗流程或接口调整 | 分别验证结果符合性与专业质量，可并行检查相同版本，最终复核须消费相关验证证据。 |
| `high` | 支付、权限、敏感资料、迁移或删除数据、生产基础设施等高风险变更 | 明确边界、失败与适用的恢复条件，环境允许时采用独立验证和复核；明示要求的独立性无法满足时，该检查保持待完成。 |

按本次变更的实际影响写明等级与理由，非软件项目使用对应的内容、授权或不可逆风险。已有岗位承担检查，不按级别固定增加岗位或启用开发。

每份检查记录包含：产物路径与版本或内容哈希、范围与标准、实际方法及结果、独立性、未覆盖项和下一负责人；复用已有记录格式，不另建平行台账。检查结论与 `DRAFT / PARTIAL` 等文档和交付状态分开：

| 结论 | 含义与返回动作 |
| --- | --- |
| `PASS / APPROVE` | 该范围内的验证或专业复核实际完成且无阻塞；文档通过不等于应用通过或用户内容确认。 |
| `FAIL / CHANGES_REQUESTED` | 有可核对的未满足标准或阻塞缺陷，附位置、条件、影响与证据，交回原负责人。 |
| `NEEDS_ENVIRONMENT / NEEDS_EVIDENCE` | 缺少具体环境、访问授权、产物或材料，交主代理解决缺口；只阻断依赖部分，不冒充产品失败或通过。 |

项目已有等效用语时保留。同一会话的自查或分阶段检查明确标为非独立；指定给其他岗位或会话的必需复核，须收到对应版本的结论才算完成，主代理自查不能代替。

复核针对实际整合稿，不能只看供稿或完成报告。检查规则、实现或生产契约、交互与验收之间的接缝，例如 API 错误字段与前端读取及用例、资源规格与接入要求、内容来源与引用。若 `message` 改成 `detail`，同步核对契约、消费端和验收示例，旧字段结论不能直接覆盖新稿。

整合后修改已复核内容时，标明差异并由原检查者判断失效范围，复核该部分及相邻影响；未变化且仍适用的证据保留。仅提交号或分支名不能标识未提交内容；文档也可用明确版本、差异和内容哈希识别。

同一验收单元的阻塞问题合并交回原负责人，默认最多两轮返工；仍有阻塞时由主代理汇总证据、分歧与选项裁决，必要时交用户，受影响部分保持未完成，不自动增加循环。非阻塞建议与风险提示单列，不单凭偏好要求返工；通过后只有新缺陷或用户新要求才重开相应范围。修订不重启无关岗位的全量检查，也不能因轮数耗尽降低标准。

## 复核、确认与维护

交付草案前核对：

- 最新目标和完整流程有覆盖，项目团队所有岗位都能定位自己的具体工作、交接和完成条件，有实际供稿或复核结果。
- 专业规则、实现契约、交互和验收之间无未处理矛盾；工作有足够细节，关键部分不依赖旧文档才能理解。
- 每份文档有维护主责与唯一写入安排，Skill 使用关系可从项目协作入口定位；事实、目标、建议、进度与执行证据未混写。
- 内容、相对链接和入口引用可用，保留旧文档；专业未决项和未完成参与如实列出，影响实施的问题不能被描述为已解决。

向用户展示草案位置、各岗实际贡献、复核结论和未决项，取得内容确认。确认后才把新文档标为已确认实施依据，并更新已约定的项目入口和 `AGENTS.md` 指向；旧材料保留并明确历史身份，避免两个入口都声称是当前依据。

后续任务按新文档实施。团队配置流程完成增岗或职责变化后，本 Skill 根据已确认交接同步修订受影响工作、交接、Skill 引用及文档主责，不反向修改角色定义或技能绑定。保留仍有效内容，实质目标或设计变更只确认受影响部分，不因再次调用而重新生成同一套文档。
